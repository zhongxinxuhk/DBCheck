安装与升级说明

  • Windows 双击 start.bat，Linux 执行 bash start.sh。
  • 首次安装账号 admin，密码 admin123。
  • 各平台包含 Java 运行时，共用 data、数据库密码密钥、台账、账号、任务、报告和自定义规则。
  • 升级前停止服务并备份整个原目录，保留 data/ 与其中的密码密钥。
  • Windows 配置迁移至 Linux 时，停止软件后复制整个 Windows-Linux-Portable 目录，再执行 bash start.sh。
  • 下载后使用 SHA256SUMS.txt 校验文件。

发布验证

Windows x64、Linux x64 和 Linux ARM64 的运行时检查与 Windows 配置迁移验证全部通过后发布。

v26.11.5.1

2026-11-09

Full Changelog: https://github.com/zhongxinxuhk/DBCheck/commits/v26.11.5.1

---

✨ 主要更新

新增：运维服务管理模块（资产 · 计划 · SLA · 审批 · 证据）

  • 新增 modules/service_management：服务资产与标识、周期采集计划、SLA 判定、make-checker 审批流、不可篡改证据链、隔离采集子进程与报表输出。
  • 采集走受控入口：客户数据模式下禁用历史直连巡检入口，改为受控采集 + 审批。
  • 独立子进程执行 JDBC 采集，超时与异常一律 fail-closed，凭据不落日志。
  • 页面：web_templates/service_management.html + 配套样式/脚本；scripts/verify_service_management.py 覆盖审批、SLA、证据、加密、越权等场景。

新增：客户数据安全边界（共用鉴权 · CSRF · 身份一致性）

  • 新增 modules/core/web_security.py 作为统一边界：会话/JWT/API Key 三种身份、浏览器 CSRF、历史报告租户隔离、公开分享关闭。
  • 身份不一致不再静默降级：当 Authorization: Bearer 指向与签名 Cookie 会话不同的账户（另一个标签页登录了别人、或 localStorage 残留旧 token），以 Cookie 会话为准并回 X-Auth-Identity-Adjusted，前端清理残留 token。此前该场景会让整站 API 401、弹窗空白。
  • 前端角色不再只信 session 快照：首页按 user_id 实时解析角色，界面权限与后端判定强制一致。

移除：强制默认口令轮换

  • 删除 /security/rotate-password 页面、/api/auth/skip-password-rotation 跳过接口、needs_rotation 闸门（页面 302 / 接口 428）与「本机激活码」校验。
  • 该机制拦住的只有自己人，没有实际安全收益；口令是否更改交由用户中心自助处理。安装期随机初始口令（16 位下限）保留。

修复：PostgreSQL 实例趋势图整块空白

  • 现象：历史趋势分析选实例后「关键指标趋势图」一片空白。
  • 根因（三处叠加）：① 指标提取的 PG 分支只认 postgres/postgresql，而实例表与历史表记录的是 pg，整段提取被静默跳过；② 连接数按 used_connections 取，采集器实际给的是 total_connections（7 个连接被记成 0）；③ 前端读 metrics.risk_count，后端只把风险数放在顶层 risk_counts。
  • 修复：新增 driver_registry.db_family() 作为唯一库族口径（pg / highgo / hgdb / opengauss / kingbase / ivorysql / vastbase / greenplum / uxdb / halodb → postgresql；mysql / mariadb / tdsqlc_mysql → mysql），指标提取、skill 自包含副本均改为按库族分派，避免同类问题在其它国产库上重复出现。

改进：趋势数据「缺什么就说缺什么」

修复：模板章节号与报告不一致（OceanBase 独有）

  • 现象（用户反馈）：OceanBase 巡检报告里「日志盘容量」显示为第 18 章，而模板管理页是第 22 章，怀疑巡检没按模板执行。
  • 根因：报告渲染会把空章节剔除后连续重排章节号（inspection_engine 的 if not queries: continue + 重排 1..N，注释原话「报告中章节序号必须连续」）。OceanBase 模板继承自 MySQL 骨架，当年只删了查询、留下 4 个章节壳，其查询数均为 0：

- 第 4 章 性能分析（OB 无对应状态变量）

- 第 7 章 复制状态检查（OB 分布式无主从）

- 第 13 章 索引使用情况（OB 不支持 performance_schema）

- 第 14 章 主从复制延迟（OB 无主从）

- 于是模板 22 章 → 报告 18 章。其余 22 种库型的模板均无空章节，编号天然一致，故只有 OB 暴露此问题。

  • 修复（init_db.py）：内置 OB 模板删除这 4 个空壳章节并重排为 1..17，日志盘容量固定为第 18 章，模板与报告逐章对齐。
  • 存量库迁移（dal.py::ensure_oceanbase_no_empty_chapters，启动时自动执行）：

- 只删「查询数为 0 且标题命中 OCEANBASE_PRUNABLE_CHAPTER_TITLES 白名单」的章节，用户自建的空章节一律不动。

- 章节号重排用两阶段更新（先全部挪到临时号段再写回），避开 UNIQUE(template_id, chapter_number) 约束冲突。

- 覆盖该库型下所有 OB 模板（含用户复制的副本），幂等，失败仅告警不影响启动。

- 调用顺序排在日志盘章节补齐（ensure_oceanbase_log_disk_chapter）之前，保证新章落到第 18 章。

修复：模板页查询显示占位 SQL

  • 现象（用户反馈）：模板管理页里日志盘三个查询全是 SELECT 'N/A' AS note FROM DUAL WHERE 1=0（实测数据本身是真实采集的，只是模板页 SQL 与执行的 SQL 不一致）。
  • 根因：v26.11.5.0 初版为集中处理 OB 版本差异，把真实 SQL 只放在采集钩子里，模板章节里播种的是占位符。
  • 修复：模板章节改存真实 SQL（模板页所见即实际执行）；采集钩子改为条件注入——仅当该 key 缺失（老库未迁移）或仍是旧占位 SQL 时注入，用户在 UI 改过的 SQL 以用户为准、不再覆盖。
  • 存量库迁移：ensure_oceanbase_log_disk_chapter 增加占位迁移，把仍是占位的行逐 key 原位更新为真实 SQL，用户改过的不动，且不重复插入章节。

  • 三步验证：compileall EXIT=0；import modules.web.app OK；discover_plugins() = 12；OB 规则 16 条（含 ob_log_disk 4 条）。
  • 本机 data/inspection.db 实况：18 章、编号连续、0 空章节、末章为日志盘容量。
